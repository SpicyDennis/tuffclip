# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

TUFFClip is a Windows-only replay-buffer clipper built with Tauri 2 (Rust core + plain HTML/CSS/JS UI in `ui/`, no Node/npm, no frontend build step). All capture/encode work is delegated to an external **FFmpeg 8+ full build** (needs `ddagrab` and `gfxcapture`; gfxcapture also does all downscaling) running on the GPU (NVENC/AMF/QSV). Git repo `SpicyDennis/tuffclip` (public; releases feed the in-app updater). Released as 1.0.0, so MAJOR now only changes for breaking changes.

## Working on changes

For every batch of requested changes: load the **suite-design** skill first (UI rules, and its "Versioning" section), follow it, and bump the version before finishing. The version lives in `src-tauri/Cargo.toml` and `src-tauri/tauri.conf.json` (keep them equal; `Cargo.lock` follows on the next build). If a change produces a UI pattern the skill doesn't cover yet, add it to the skill.

## Commands

Run from `src-tauri/` unless noted:

- Dev with live reload: `cargo tauri dev`
- Release build: `build.bat` in the repo root (runs `cargo tauri build --no-bundle`, copies `target\release\tuffclip.exe` to `build\TUFFClip v0.0.0.exe`, the version read from `Cargo.toml`, older `TUFFClip*.exe` in `build` deleted; the cargo step goes through `build-heartbeat.ps1`, which prints "still working" every 15 s because the LTO link is silent for minutes; it does not bundle ffmpeg, the app downloads it into the data dir on first run). Needs `cargo install tauri-cli --version "^2" --locked`.
- Publish a release: `release.bat` in the repo root (after `build.bat`): `gh release create v<version>` with the built exe attached. The in-app updater only sees releases of a **public** repo.
- Type-check only: `cargo check` (`cargo clippy` is clean apart from Win32 struct-init style hints)
- Unit tests: `cargo test` (pure logic: bitrate, crop, ffmpeg args, RAM keyframe cutting, track picking, sound conversion, export sound mixing, versions, settings compatibility).
- Live tests: `cargo test -- --ignored --test-threads=1` (`live_tests.rs`): record display (RAM, 3 tracks), display below native (gfxcapture), a cropped region, and a Notepad window, save clips, export every format/mode. Needs FFmpeg on PATH + NVIDIA; about 1 minute; opens and closes Notepad.
- Driving the real UI: debug build run as `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333 target\debug\tuffclip.exe`, then CDP `Runtime.evaluate` against the page from `http://127.0.0.1:9333/json` (app.js globals like `S`, `snd`, `bench`, `renderExport` are reachable). It shares the data dir and WebView2 localStorage with the real app: back up `config.json`/`exported.json`, point `clips_dir` at a scratch folder, never click Reset all settings (it turns Start with Windows off), and delete test benchmark entries afterwards.

The `windows` crate is 0.58; expect occasional signature differences from newer docs.

UI follows the suite-design skill (Slate & Tally). theme.css is the shared theme; don't edit it per app. Settings follow the skill's fixed order. Deliberate deviations, per the owner's requests: settings autosave (no draft/Save bar); no File menu (menu.js was removed in 1.0.0; Ctrl+, / Ctrl+Q / Esc still work, Open data folder lives in Settings > Advanced); no Back button in Settings (tab or Esc leaves); the top bar holds quick settings (clip length, resolution, frame rate) in the middle and a reminder of the clip shortcut at the far right.

## Recent behaviour worth knowing

- Distribution: `build\TUFFClip v0.0.0.exe` is meant to be handed out alone. `.cargo/config.toml` links the MSVC CRT statically (`+crt-static`) so no VC++ Redistributable is needed; WebView2 is the only external runtime (preinstalled on current Windows 10/11). Don't add files that must sit next to the exe.

- Games mode defaults to `capture_method: window`: ffmpeg's `gfxcapture` (Windows Graphics Capture) records only the game's HWND, so windows in front never show; resizes are letterboxed (`resize_mode=scale_aspect`) instead of restarting, and `fps=` pads the variable frame rate. `capture_method: display` is the old path: ddagrab cropped to the window's client rect (`recorder::crop_for`), where a changed rect must hold still 3 s before ffmpeg restarts (`Engine::resolve_crop`). Desktop mode is always ddagrab.
- Several listed games running: `Engine::update_tracked` picks the one with the most raw clips and then sticks to it (switching restarts the buffer); the top-bar selector calls `set_target`.
- When the game closes, `Engine::keep_or_discard` stops ffmpeg but keeps the buffer (`Held`: RAM `Arc<RamBuf>` or the segment dir) for `hold_minutes`; `save_clip_inner` falls back to it. A new recording drops it.
- `exported.json` (data dir) maps raw clip -> its export files (`library::record_export`); `Clip.exported` and the Storage cleanup use it. Renames/deletes must keep it in sync.
- Export file type/codec are per-export (UI + `ExportRequest`), not settings. `gentle_save` (alias of old `export_gentle`) only affects saving raw clips.
- Window X / minimize: `close_to_tray` (default on; off = X calls `app.exit`) and `minimize_to_tray`. `hide_window`/minimize use `destroy()` so they never trigger the quit path. `tauri-plugin-single-instance` must stay the first plugin.
- `buffer_in_ram`: ffmpeg writes MPEG-TS to stdout, `RamBuf` cuts it at video-PID (256) keyframes; saving pipes the chunks to ffmpeg stdin. Disk mode is the segment ring as before.
- Crash handling is retry-with-backoff forever (`Engine::note_crash`), plus a stall watchdog; the watcher tick is wrapped in `catch_unwind`.
- `.gif` export (`export.rs`): single ffmpeg pass with palettegen/paletteuse, no audio, own fps/size selects (`#gifFps`, `#gifRes`); exported gifs are not listed in the library. Settings codec defaults to HEVC (existing settings keep their value). Export progress shows percent + time left only (no speed). Games get their display name from the game list; adding a running app uses the optional "Name to show" field, not the window title.
- `.png` export (`export::export_frame`) is a screenshot: the frame under the playhead, decoded raw from the clip with one ffmpeg call, no filters, lossless. Picking `.png` hides the mode/size/bitrate/codec/resolution/low-impact controls and the button reads "Save frame". They go in `Exports\<Game>\Screenshots\`. Like gifs, pngs aren't listed in the library and don't mark the raw clip as exported.
- Exports run at normal priority on all cores unless the export area's "Low impact" is ticked (idle priority, half the threads); stream copies and saving raw clips are separate (`gentle_save`). `.webm` always re-encodes (VP9 + Opus); "original quality" with a different codec is a quality-matched GPU re-encode (`HEVC_RATIO` 0.65, duplicated in `ui/app.js`), audio copied.
- `fps: 0` means "native": the monitor refresh rate from `EnumDisplaySettingsW`.

- Bitrate is automatic by default (`bitrate_auto`): `config::auto_bitrate` (output size x fps^0.75 x 0.2 bpp, HEVC x0.65) is applied in `RecordSpec::apply_auto_bitrate`; `autoRate` in `ui/app.js` mirrors it for display. The settings field is locked until "Set the bitrate myself" is ticked.
- Renaming a game in Settings > Games moves its `Raw\<Game>` / `Exports\<Game>` folders (`library::rename_game`, called from `apply_config`) and rewrites `exported.json`; file names don't change. Names apply on blur, not per keystroke. Games added get their exe name (editable afterwards).
- `show_main` retries (window still closing, WebView2 hiccup) so opening from the tray or a second launch can't silently do nothing; `memory_info` runs off the main thread so a busy recorder can't freeze the window.

- Recording indicator (0.10.0): the yellow border around a captured window is drawn by Windows Graphics Capture (the recorder passes `display_border=0`, which only works where Windows allows it). TUFFClip's own indicator is `overlay.rs`: one 12 px dim click-through dot on a corner of the game window, shown only while that window is in front. Position is `Config.indicator`, overridable per game (`GameEntry.indicator`), or Off. On a save, `Engine::save_clip` calls `overlay::flash(ok)`: the dot grows and pulses green (red on failure) for 1.4 s. The sound is the separate `beep` setting.
- 0.12.0: the dot is 22 px / ~85% opaque (`overlay.rs` `DOT`, `ALPHA`). Settings > Games shows buttons that open modal dialogs (`#gamesDlg`, `#ignoredDlg`) holding the lists, each with a search box (`filterRows` hides non-matching rows). `start_key_poll` (`main.rs`) polls the clip hotkeys with `GetAsyncKeyState` every 40 ms while recording or holding a buffer, as a backup for the registered global shortcuts (`save_clip` ignores a second save within 1 s).
- Preview tab (`preview.rs`): a second low-priority ffmpeg built from the recorder's current `RecordSpec` (5 fps, 960 px wide, mjpeg to stdout) that emits `preview-frame` events (base64 JPEG). It starts only while the Preview tab is open and visible and is killed on tab switch, hide and window destroy.
- `Config.ignored_exes` hides programs from the "Add a running app" list (`list_windows` filters them); edited in Settings > Games.
- Self-heal (`start_self_heal` in `main.rs`): a thread pings the main thread every 10 s; if it hasn't answered for 90 s, TUFFClip relaunches itself (`--hidden --relaunch`, which waits 3 s so the single-instance hand-off doesn't hit the dying copy) and exits. Goal: a hung background instance must never stop you opening TUFFClip.

- 0.13.0 capture card (a console over a USB HDMI card): the card has no passthrough and Windows lets one program open it at a time, so TUFFClip doesn't open it with ffmpeg. Instead the `capture` window (`ui/capture.html`, `show_capture`, opened from the top bar or Settings > Capture card) shows it with `getUserMedia` (picture + sound, card picked by name / `groupId`, never a mic by guess) and reports its size/fps via `capture_feed`. `Engine::update_tracked` treats that window as the game (`CAPTURE_EXE`, named `Config.capture_name`, default "Capture card"; it wins over running games), always window-captured with `RecordSpec.force_size` so gfxcapture outputs the card's resolution whatever the window size, fps capped at the card's. Sound comes from the normal loopback. Renaming `capture_name` moves its folders like a game rename. The window is destroyed on close (`set_feed(None)`).

- 0.18.0 sound tracks: `audio::plan` picks the tracks from `Config.audio_source` (`game` = process loopback on the tracked game's pid tree via `ActivateAudioInterfaceAsync`, falls back to desktop loopback on old Windows; `desktop` = default output loopback; desktop capture mode always uses desktop), `discord_track` (process loopback on the root Discord process, `win::discord_pid`, re-attached when Discord starts/restarts) and `mic` / `mic_device` (empty = Windows default; follows default-device changes). `RecordSpec.tracks` is set in `Engine::tick`. With 2+ tracks the recorder's filter graph splits the pipe with `asplit`+`pan` into a mix (stream a:0) plus one stream per source. `Layout::pick` chooses what a saved clip keeps: separate tracks silent during the clip are dropped, and if only one source was heard the clip keeps just the mix under that source's name. Titles go in as `title` + `handler_name` (`recorder::audio_maps`). The windows crate's `#[implement]` macro needs `windows_core` to be 0.58, so webview2-com's 0.62 is renamed `wv_core` in Cargo.toml.
- Library sound levels: `clip_audio` (`sound.rs`) decodes each audio track to `.playback\<clip>_a<N>.flac` (aligned with `first_pts=0`) plus a `.peaks` waveform (20/s); `sound::prune` keeps 8 video proxies and 32 tracks. The viewer (`loadSound` in `app.js`) plays the parts (not the stored Mix) as `<audio crossorigin>` elements through Web Audio gains in step with the video; the video's own sound is routed through Web Audio too (needs `video.crossOrigin`, retried without on error) and silenced while tracks play, and its volume/mute act as master. Levels live in localStorage `clipr.levels` per clip path (moved on rename, dropped on delete). Export gets `levels` (`ExportRequest.levels`): null = copy track 0 (the mix); otherwise `volume`+`amix normalize=0` into one track, the video still stream-copied in original mode.
- 0.20.0 Benchmark tab (`bench.rs`, `etw.rs`): `bench_start` runs `rounds` × (on, off) phases in ABBA order; `Engine::bench_pause(true)` stops ffmpeg and makes `tick` skip recording (status/tray show `Status.bench`), `false` resumes via `config_changed`. Each phase skips `WARM_SECS` after a switch and only keeps seconds where the game (`Engine::bench_target`, never the capture card) is in front and the recording state matches. Basic = PDH `\GPU Engine(*)\Utilization Percentage` (query rebuilt per phase so a new ffmpeg pid shows up) + `GetSystemTimes`/`GetProcessTimes`. Full = also frames: TUFFClip re-runs its own exe as `--bench-helper <out> <ctl> <parent pid>` (handled at the top of `main()`, before the single-instance plugin), first as a normal child, and through `ShellExecuteExW runas` only if it writes `error denied` (StartTrace access denied; admins and "Performance Log Users" don't need UAC). The helper runs an ETW real-time session ("TUFFClip Benchmark", QPC timestamps via `ClientContext=1` + raw timestamp mode) on Microsoft-Windows-DXGI (Present_Start 42, PresentMultiplaneOverlay_Start 55) and D3D9 (1), writes one QPC per frame of the pid named in the ctl file, and stops on `stop`, parent exit or 30 min. Results pair each round's on/off and report mean ± 95% t-range; the UI words the verdict (`benchVerdict` in `app.js`) and keeps the last 8 in localStorage `clipr.benchHist`. Verified: the helper counted 165 fps from a Chromium GPU process on a 165 Hz screen; PDH reads without admin.

## Architecture

The key design goal is near-zero idle cost; several choices follow from it:

- **No webview while gaming.** `main.rs::show_main` creates the `main` window on demand (in a spawned thread, to avoid a Windows deadlock) and it is destroyed on close. `windows: []` in `tauri.conf.json` is intentional. `RunEvent::ExitRequested` is prevented so the app lives in the tray; only the tray "Quit" (`app.exit(0)`) exits, which triggers `Engine::shutdown`.
- **`Engine` (`engine.rs`)** is shared as `Arc<Engine>` Tauri state. `run_watcher` is a 1 Hz loop that checks the foreground process (`win.rs`) against the configured mode (`CaptureMode`: games-only vs. always-record a monitor), and starts/stops/restarts the recorder. Changing settings calls `eng.config_changed()`; anything in `RecordSpec` that differs forces an ffmpeg restart. Status is pushed to the UI via Tauri events.
- **`recorder.rs`** builds and supervises the single long-lived ffmpeg process: ddagrab (or gfxcapture for a window / a downscaled display) -> HW encoder -> 2 s MPEG-TS segments in a rotating ring (`SEG_SECS`). Saving a clip stitches the newest segments with `-c copy` (no re-encode), so clip length is only accurate to about ±2 s.
- **`audio.rs`** captures sound with raw WASAPI (no cpal), one thread per track, and feeds ffmpeg's stdin as one paced multichannel f32 stream (10 ms steps, silence-filled; track k = channels 2k/2k+1, all 48 kHz stereo) so the tracks stay sample-locked and ffmpeg never stalls. See "Sound tracks" below.
- **`win.rs`** holds the raw `windows`-crate code: DXGI monitor/adapter enumeration, foreground process lookup, window list, and the Job Object that ties ffmpeg's lifetime to TUFFClip (no orphaned ffmpeg after a crash).
- **`export.rs`** does trim / target-size export with progress events (`export-progress`): stream copy for "original", GPU encode at a computed bitrate (retried once on overshoot), or x264 two-pass for "exact size".
- **`library.rs`** lists clips from per-game folders: `<clips_dir>\Raw\<Game>\` and `<clips_dir>\Exports\<Game>\` (default `Videos\TUFFClip`). `config.rs` persists JSON settings and `ffmpeg.log` in `%LOCALAPPDATA%\TUFFClip\`. `ff.rs` wraps ffmpeg invocation (always `CREATE_NO_WINDOW`) and the capability check.
- **IPC surface** is the `#[tauri::command]` list in `main.rs`; the UI (`ui/app.js`) calls them through `withGlobalTauri` (`window.__TAURI__`). Adding a command means registering it in `generate_handler!` and calling it from `app.js`.
- **Security constraints:** the CSP and `assetProtocol` in `tauri.conf.json` control video playback; `main.rs` adds the clips dir to the asset scope at startup and whenever it changes. File-deleting commands must go through `inside_clips_dir` (canonicalized path must be under the clips dir).
- **Hotkeys** (default Alt+F10, plus an optional `hotkey2`) are registered via `tauri-plugin-global-shortcut` (`set_hotkeys`); `save_config` re-registers them and rolls back to the old ones on failure. `tray.rs` owns the tray icon (red dot while recording) and tooltip, updated from `Engine::update_tray`.

- Renamed from Clipr to TUFFClip in 0.9.0: crate/exe `tuffclip`, data dir `%LOCALAPPDATA%\TUFFClip` (`config::data_dir` renames an old `Clipr` dir once), startup Run key `TUFFClip` (the old `Clipr` key is deleted on the next toggle). Existing `clips_dir` settings keep their saved path; only the default for new installs is `Videos\TUFFClip`. The logo is `src-tauri/icons/icon.png` (and `ui/logo.png` for the top bar); localStorage keys stay `clipr.*` so saved preferences survive.

- 0.14.0: the top-bar selector (`#targetSel`, always visible) lists "Games (automatic)", running games, and one "Desktop · <monitor>" per monitor; picking one sets `Config.mode` / `monitor` (so Settings > Capture follows) and calls `set_target`. The clip shortcut at the top right is a button opening `#hkDlg` to re-record it.
- 0.12.1: WebView2 may not decode HEVC (black viewer). `selectClip` probes the codec and, for `hevc`, `loadVideo` plays an H.264 copy from `playback_proxy` (`<clips_dir>\.playback`, newest 8 kept, made with libx264 ultrafast at idle priority). Trim/export still use the original file.

- 1.0.1 FFmpeg download: `ff::FFMPEG_URLS` tries BtbN's **n8.1** release build first (then n9.0, then master). 9.0 and master (BtbN and Gyan alike) are built against NVENC API 13.1 and need NVIDIA driver 610+; on older drivers every recording fails with "Driver does not support the required nvenc API version" (seen on friends' PCs; the owner's 610.74 hid it). 8.1 needs API 13.0 / driver 570+ and has the same gfxcapture options; all live tests pass on it. `recorder::copy_log` spots that message (`nvenc_driver_too_old`, cleared after 30 s of good recording), the status says so and `FfInfo.driver_too_old` shows the strip with "Download FFmpeg again". `FfInfo.path` (`ff::resolve`, PATH lookup) fills the location box with the real ffmpeg.exe path while the setting itself stays "ffmpeg" (`ffShown` in app.js).
- 1.0.2 clip saves: `save_ram`/`save_buffer` pass `recorder::PROBE` (`-probesize 100M -analyzeduration 10M`). ffmpeg's default 5 MB probe is ~0.3 s at 1440p165 ~113 Mbps; when it held no packet of a sound track, ffmpeg failed with "sample rate not set / Could not write header" and left a 0-byte mp4 in the library (seen once on League). A failed save now deletes its output (`save_clip_inner`) and is written to `ffmpeg.log` (`note_save_error`, "Saving <path> failed: ...").
- 0.15.2: the FFmpeg download was BtbN's *master* build (until 1.0.1), so options can vanish under us. Recent master dropped input-side `-thread_queue_size` (ffmpeg refused to start, "ffmpeg keeps stopping"); `ff::input_queue_size_ok` probes for it once per ffmpeg path and the recorder only passes it when accepted.
- 0.15.0 camera access: the capture window never triggers a camera prompt. `Config.camera_access` (default false) is the gate: `gate_camera` (`main.rs`) answers WebView2's PermissionRequested from it (never saved by WebView2). Until allowed, the window shows "Look for capture card" (`set_camera_access(true)`). There is deliberately no "remove access" button (tried in 0.15.0, dropped in 0.15.1). `save_config` ignores the incoming `camera_access`.
- 0.17.0 self-update (`update.rs`): off by default; `Config.check_updates` (Settings > About) gates every network call (`update_check` / `update_install` refuse while it's off). Checked at most every 15 minutes (0.19.0; was once a day): `start_update_poll` (`main.rs`) wakes every minute and calls `update::check(false)`, which only goes online when `update.json` (data dir; `checked_at` Unix seconds + result; a failed check isn't cached) is 15 minutes old, and emits `update-available` to an open window; the window also checks when it opens; a newer release shows the `#updBanner` strip. Install: curl the release's `.exe` asset to `TUFFClip.update.part` beside the running exe, check size / `MZ` / GitHub's sha256 `digest` (certutil), rename the running exe to `TUFFClip.old.exe`, put the new one in place (renamed `TUFFClip v<new>.exe` if the old name followed that pattern, else the same name), start it with `--relaunch --updated`, exit. `--updated` waits until `TUFFClip.old.exe` can be deleted (old copy gone, max 30 s) instead of the 3 s relaunch sleep, opens the window, re-points the Start with Windows key at the new path (0.18.4: every release-build start does this via `fix_autostart_path` whenever the key names a different exe, so a new `build.bat` exe takes over too; dev builds only on `--updated`), and toasts the new version. A folder TUFFClip can't write to (Program Files) gets the releases page in the browser instead. Testing without publishing: in a **debug** build only, `TUFFCLIP_UPDATE_FEED=file:///.../feed.json` (GitHub release JSON with a `file:///` asset URL) replaces the GitHub API; run the debug exe from a scratch folder as `TUFFClip v<cur>.exe` with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` to drive the UI over CDP. Back up `config.json` first (the test copy shares the data dir), and if Start with Windows is on, note the `HKCU\...\Run` `TUFFClip` value: the updated test copy re-points it at itself. Windows Defender may flag the downloaded exe as `Trojan:Win32/Bearfoos.A!ml` (ML false positive for unsigned self-updaters; the same bytes in `build\` aren't flagged).
